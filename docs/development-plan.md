# 開発方針と最初の検証

機能実装よりも、変更しやすい責務分離と未検証事項の確認を優先します。必要になるまでフレームワーク、ライブラリ、ビルド基盤、CI、データベース、Docker構成を導入しません。

## 最初のIssue候補：Firefox＋InboxSDKでGmail連携を検証する

### 目的

Firefox拡張からInboxSDKを使い、Gmailの作成・返信画面を検出し、送信要求に必要な情報がどこまで取得できるか確認する。InboxSDK採用可否と次のAPI設計に必要な根拠を得る。

### 最小スコープ

- 検証用の小さなFirefox拡張を作り、InboxSDKの読み込みと必要な権限を確認する。
- 新規ComposeとReplyを手動で開き、検出・識別・情報取得を確認する。
- テスト用アカウントと架空の本文を使い、Gateway・SMTP接続なしで結果を確認する。
- 実メール内容・Token・アカウント情報をコミットせず、結果は匿名化して記録する。

### 確認する項目

| 項目 | 確認内容 |
| --- | --- |
| Firefoxでの動作 | Firefox／InboxSDKのバージョン、読み込み方式、拡張マニフェスト、必要権限、制約。 |
| Compose検出 | 新規作成、閉じて再作成、複数の作成画面で正しい画面を識別できるか。 |
| Reply識別 | 新規作成と返信を区別できるか。通常返信と全員に返信で比較する。 |
| To | 複数宛先、編集後の値、表示名とメールアドレスの取得。 |
| Cc | Ccなし・あり・編集後の値の取得。 |
| Subject | 新規作成と返信で件名を取得できるか。 |
| Body | プレーンテキスト／HTMLの取得範囲、編集反映、引用文・署名の扱い。 |
| 元メールとの関連 | 元メッセージ、スレッド、元メール宛先など、返信先のIdentity判定に使える情報。 |
| Message-ID | RFC Message-IDそのものか、Gmail／SDK内部IDかを区別し、取得元を記録する。 |
| References | 元メールの参照列が取得できるか、欠落や制限があるか。 |
| In-Reply-To | 返信対象のRFC Message-IDを取得し、ヘッダーに利用できるか。 |

転送後のメールで独自ドメインの元宛先が残るかも確認し、返信Identityを自動判定できると仮定しません。元メールのMessage-IDと新しく送るメール自身のMessage-IDは区別します。

### 成果物と完了条件

- 最小PoCコードと、Firefoxへの読み込み・再現手順。
- 各項目を「取得可能／条件付き／取得不可／未確認」に分類した結果表。
- 取得に使ったSDK API、必要な追加手段・権限、値の意味と制約の記録。
- 新規作成・返信・全員に返信での確認結果、および匿名化した出力例。
- InboxSDKを採用するか、追加検証が必要か、その理由。
- 次に決められるAPI項目と、まだ決められない項目の一覧。

情報を取得できないという結果も有効な検証成果です。未取得項目を推測で補わず、代替手段が必要なら別Issue候補として提示します。InboxSDKで不足する場合も、Gmail API全面依存や大規模な独自DOM解析へ自動的に方針転換しません。

### 対象外

実メール送信、Gateway実装、管理UI、完成版の送信ボタン、添付ファイル対応、他ブラウザ対応、Gmail標準送信の置き換えは行いません。

## PoC後の小さな開発順序

1. **送信APIの最小契約を文書化する。** Identity取得と送信のパス・入出力、返信情報、本文形式、認証エラー、SMTP受付結果の意味、重複送信の扱いを決める。
2. **Gatewayの最小構成を選定する。** 言語・永続化・秘密情報管理と管理経路を決め、単一Identity／単一Profileで認証・From検証・汎用SMTP送信を試せる最小実装に絞る。モデルは複数登録を妨げない。
3. **隔離したテスト環境で配送を確認する。** Archive BCC、返信ヘッダー、Token失効、エラー時の挙動を確認する。
4. **拡張から接続する。** 設定可能なGateway URLとTokenを使い、利用者の明示操作で送信する最小フローを作る。
5. **常用のための管理・運用を整える。** 管理UI、永続ボリューム、Docker、ログ、公開経路を実装・検証する。外部公開前に未認証API拒否と管理経路遮断を確認する。

各段階で必要な依存だけを追加します。現時点では上記手順の実装を開始しません。

依存を追加する際は、InboxSDKを含め対象バージョンのライセンスと必要な表示を確認します。第三者コードに含まれる著作権・ライセンス表示を保持し、配布時に必要なライセンス全文やNOTICEも同梱します。依存の導入時に名称・バージョン・入手元・ライセンスを記録し、必要に応じて第三者表示用ファイルを追加します。

## 未決定事項

- FirefoxでのInboxSDK互換性、APIで取得可能な情報、SDK利用条件と必要な登録・権限。
- Gateway／拡張の言語、フレームワーク、ビルド方法、データベース。
- APIスキーマ、Identity取得パス、バージョニング、本文形式・サイズ制限、添付ファイル・通常BCCの対応範囲。
- 返信ヘッダーの生成方法、元宛先からのIdentity判定、Gmail上でのArchive BCC表示。
- API Tokenの生成・ハッシュ方式、Identity単位の権限が必要か、拡張側の安全な保存方法。
- SMTPのTLS設定範囲、タイムアウト、再送・冪等性、同期／非同期送信。
- 管理UI認証、初期セットアップ、CSRF対策、プロキシ信頼設定、ポート分離とTLS終端。
- 永続化形式、SMTP秘密情報の暗号化・鍵管理、バックアップ、ログ項目・保持期間。
- 拡張のネットワーク権限とCORS、外部公開APIの流量制限。
- 将来の簡易作成画面、Tailscale、他ブラウザ対応の具体的な仕様。

これらは実装に必要となる段階で判断し、現時点で大きな仕様を追加しません。
